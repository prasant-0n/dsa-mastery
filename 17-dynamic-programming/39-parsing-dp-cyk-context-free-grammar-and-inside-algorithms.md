# 39 — Parsing DP: CYK, Context-Free Grammar & Inside Algorithms

## 1. Why Parsing Is Dynamic Programming

Many parsing problems ask whether a sequence can be generated by a grammar, how many parses exist, or which parse has the best score.

The key decomposition is an interval plus a grammar state:

```text
dp[nonterminal][l][r]
```

The interval is split at a boundary `k`, and the two resulting spans are combined according to a grammar production.

This is interval DP with a symbolic state space.

---

## 2. Context-Free Grammar Model

A context-free grammar contains:

- terminals;
- nonterminals;
- productions;
- a start symbol.

A production may look like:

```text
A → B C
A → terminal
```

For a binary production `A → B C`, a parse over `[l, r)` exists when some split `k` satisfies:

```text
dp[B][l][k] && dp[C][k][r]
```

The parser must define whether empty productions and unit productions are supported.

---

## 3. CYK Preconditions

Classic CYK parsing assumes a grammar in Chomsky Normal Form (CNF): productions are essentially:

```text
A → B C
A → terminal
```

Transforming a grammar into an appropriate normal form can simplify the parser but may increase grammar size.

Do not silently assume CNF when the input contract permits arbitrary CFG rules.

---

## 4. Boolean CYK

For a token sequence of length `n`, define:

```text
dp[A][l][r] = whether A derives tokens[l..r)
```

Base intervals have length one and use terminal productions.

For increasing span length:

```text
for length = 2..n:
    for l:
        r = l + length
        for split k:
            combine left/right nonterminal states
```

The start symbol determines whether the complete sequence is accepted.

With a grammar containing `G` binary productions, a straightforward implementation is roughly cubic in `n`, multiplied by the relevant grammar transition work.

---

## 5. Inside Algorithm

CYK is not limited to Boolean recognition.

Replace Boolean OR/AND with an algebra appropriate to the task.

For counting:

```text
inside[A,l,r] += inside[B,l,k] * inside[C,k,r]
```

For minimum cost:

```text
inside[A,l,r] = min(
    inside[A,l,r],
    inside[B,l,k] + inside[C,k,r] + ruleCost
)
```

For probabilities, the corresponding product/sum recurrence gives an inside-style probability computation when the grammar model is defined appropriately.

The broader lesson is **semiring parsing**: the interval structure stays fixed while the value algebra changes.

---

## 6. Parse Forests and Ambiguity

A grammar may have multiple valid parses for the same input.

Do not confuse:

- recognition: does at least one parse exist?
- counting: how many parses exist?
- best parse: which parse has minimum/maximal score?
- enumeration: list every parse.

Enumeration can be exponentially large even when the DP table is polynomial.

A shared packed parse forest can represent many derivations compactly without materializing every tree immediately.

---

## 7. Backpointers and Viterbi Parsing

For optimization, store the production and split that produced the selected value:

```text
parent[A,l,r] = { rule, split, leftState, rightState }
```

Backtracking through these decisions reconstructs one optimal parse.

If deterministic output is required, define tie-breaking explicitly rather than relying on rule order or hash-map iteration.

---

## 8. Counting Parses Correctly

Ambiguous grammars require special care.

A derivation count is not automatically the same as the number of distinct tree structures, token segmentations, or semantic interpretations.

Before writing the recurrence, define exactly what one counted object represents.

Then test tiny grammars by exhaustive derivation enumeration.

---

## 9. Unit and Epsilon Productions

Rules such as:

```text
A → B
A → ε
```

break the simplest binary-span recurrence.

Possible strategies include:

- convert the grammar to a suitable normal form;
- compute unit-closure separately;
- represent nullable nonterminals explicitly;
- use a more general chart parser.

The transformation must preserve the intended semantics, especially when counting derivations where closure can introduce multiplicities.

---

## 10. Earley-Style State Thinking

General CFG parsing can use chart states such as:

```text
(A → α • β, origin)
```

The dot records how much of a production has been recognized.

The important DP insight is that equivalent parser states are memoized instead of recomputed.

The three conceptual operations are commonly described as:

- predict;
- scan;
- complete.

This is a bridge from interval DP to state-chart parsing.

---

## 11. Tokenization Is Part of the State Contract

A parser operates on a sequence of symbols, not raw characters unless characters are the intended terminals.

Decide whether the input is:

- bytes;
- Unicode code points;
- lexical tokens;
- subword tokens;
- application-specific symbols.

In JavaScript, indexing a string operates on UTF-16 code units. If grammar terminals represent Unicode code points, normalize the representation first.

---

## 12. Weighted and Probabilistic Grammars

A production can carry a weight or probability:

```text
A → B C   weight = w
```

The recurrence combines child values and the rule weight.

For probability products over long spans, underflow can become a problem. Log-space converts products into sums:

```text
log(pq) = log(p) + log(q)
```

Then the additive combination across alternatives becomes log-sum-exp when exact probabilistic aggregation is required.

---

## 13. Semiring View

A useful abstraction uses two operations:

```text
⊕ = choose/combine alternatives
⊗ = combine child derivations
```

Examples:

| Task | `⊕` | `⊗` |
|---|---|---|
| Recognition | OR | AND |
| Counting | + | × |
| Min-cost | min | + |
| Max-score | max | + |
| Probability | + | × |

The parsing recurrence remains structurally identical.

This is a powerful connection between DP and algebraic dynamic programming.

---

## 14. Sparse vs Dense Charts

A dense chart allocates every nonterminal/span combination.

A sparse chart stores only states that are reachable.

Dense storage can be faster when the grammar is small and most states are active. Sparse maps can save memory for highly constrained grammars.

The right representation depends on grammar density, input length, and the cost of map operations.

---

## 15. Grammar Indexing

Naively scanning every grammar rule for every split can dominate runtime.

Pre-index binary productions by child pair:

```text
(B, C) → [A1, A2, ...]
```

Then when `B` and `C` are available, only compatible parent rules are considered.

Other useful indexes group rules by:

- left child;
- right child;
- terminal;
- nonterminal.

Indexing is an engineering optimization, not a change to the recurrence.

---

## 16. Inside-Outside Connection

The inside algorithm summarizes a span from the bottom up.

Outside values summarize the context surrounding a span.

Together they support tasks such as expected rule counts and parameter estimation in probabilistic grammar models.

The conceptual connection is similar to rerooting: local state is propagated from both the inside structure and the surrounding context.

---

## 17. Constraint and Pruning Strategies

Exact parsing can still have a large constant factor.

Useful pruning conditions include:

- impossible token/nonterminal pairs;
- minimum derivable span length;
- maximum derivable span length;
- lexical compatibility;
- score bounds;
- beam-like approximate pruning when exactness is explicitly relaxed.

Never mix approximate pruning into an exact algorithm without documenting the semantic change.

---

## 18. Reconstruction and Forest Compression

Storing every parse tree defeats the purpose of dynamic programming when ambiguity is large.

Prefer compact representations:

```text
node = (nonterminal, l, r, rule, split)
```

Shared nodes can be referenced by IDs.

A packed forest can then support lazy reconstruction, best-parse extraction, counting, or downstream transformations.

---

## 19. Complexity

For `n` tokens and a binary grammar, the interval dimensions contribute:

```text
O(n²) spans × O(n) splits = O(n³)
```

Additional factors depend on how grammar rules and nonterminal combinations are indexed.

Memory is typically `O(n² × |N|)` for a dense chart, where `|N|` is the number of nonterminals.

Do not hide grammar size inside an unexplained `O(n³)` claim.

---

## 20. Correctness Proof Template

For Boolean CYK:

1. define `dp[A,l,r]` precisely;
2. prove length-one initialization from terminal rules;
3. assume shorter spans are correct;
4. show every binary derivation has a unique top production and split;
5. show every recurrence candidate corresponds to a valid derivation;
6. conclude the table is exact.

For counting or optimization, replace existence with the corresponding algebraic invariant.

---

## 21. Testing Strategy

Build independent tiny oracles.

Test:

- empty input where supported;
- one-token input;
- impossible strings;
- ambiguous grammars;
- nullable/unit rules;
- duplicate productions;
- repeated tokens;
- long chains of unary derivations;
- many equivalent parses;
- deterministic tie-breaking;
- exact counts using `BigInt`;
- weighted/probabilistic numerical stability.

For counting, exhaustive enumeration is essential on very small grammars.

---

## 22. Differential and Metamorphic Testing

Useful properties include:

- CNF-transformed grammar agrees with the original semantics;
- rule-order permutation does not change value;
- equivalent token relabeling preserves acceptance;
- adding an unreachable grammar rule changes nothing;
- Boolean recognition agrees with whether the count is nonzero;
- best-parse score agrees with the score recomputed from the reconstructed tree.

These tests catch state-indexing and grammar-normalization errors.

---

## 23. Backend Applications

Parsing DP appears in:

- expression evaluators;
- configuration languages;
- query languages;
- document structure validation;
- workflow DSLs;
- rule engines;
- protocol/message grammars.

A backend parser should enforce input-size and grammar-size limits because cubic or worse chart work can become a denial-of-service vector.

---

## 24. AI Engineering Applications

Parsing DP connects directly to AI systems that work with structured sequences:

- syntactic parsing;
- probabilistic grammars;
- constrained generation;
- structured prediction;
- program-language parsing;
- semantic or compositional structure search.

The inside algorithm is also a useful mental model for dynamic programming over latent hierarchical structures: many local derivations share the same span/state summary.

---

## 25. Interview Recognition Framework

When a problem mentions a grammar and a sequence, ask:

1. Is the grammar context-free?
2. What exactly is one state: nonterminal + span, or a chart item?
3. Are productions binary, unary, or nullable?
4. Is the task recognition, counting, optimization, probability, or reconstruction?
5. Can the grammar be normalized safely?
6. What is the split variable?
7. What algebra combines alternatives and child derivations?
8. Is the chart dense or sparse?
9. What is the true grammar factor in the complexity?
10. How will ambiguity and reconstruction be represented?

---

## 26. Master Pattern

```text
Sequence + CFG
      ↓
Define parser state
      ↓
Choose span/chart decomposition
      ↓
Normalize or support rule forms
      ↓
Initialize lexical/empty states
      ↓
Combine smaller states
      ↓
Choose algebra
  ↙       ↓        ↘
OR/AND   +/*      min/+
  ↓       ↓        ↓
recognize count   optimize
      ↓
store compact witness / forest
      ↓
prove + differential-test
```

The central insight is that **parsing is dynamic programming over derivation structure**. CYK provides the clean interval formulation; chart methods generalize the state space; the inside algorithm shows that the same structural DP can operate over multiple algebras.
